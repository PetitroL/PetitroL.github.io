给简历做一次体检：JD × 简历匹配到底该怎么打分

2026-11-20

找工作最耗时间的不是投简历，是判断「这份 JD 值不值得我花半小时改一版简历」。招聘网站给的那个百分比只会告诉你「匹配 78%」，从来不告诉你差在哪、能不能补、怎么补。

所以我做了 JobFit：把一份 JD 和一份简历放进去，得到 0-100 的匹配分、五个维度的扣分原因、以及每条都能直接复制到简历里的改法。不投递、不外发，简历不出本机。

源码仓库：PetitroL/jobfit

想把「差在哪」拆到能动手的程度

同样是「不匹配」，其实有三种完全不同的情况，处理方式天差地别：

  • 差的是硬门槛技能（JD 要 Kubernetes，你完全没有）→ 这个岗位现在够不着，别浪费时间；
  • 差的是表达（你做过，但简历里没写）→ 改一句话就能过筛，性价比最高；
  • 差的是级别（JD 要 8 年，你 7 年）→ 心里有数，面试时能聊。

工具的价值不是给一个分数，而是把这三件事分开说清楚。

五个维度，100 分怎么分

维度 满分 怎么算 为什么这么定
硬技能匹配 40 识别 JD 里提到的技能（46 个词条，带别名），按权重加权算命中比例；加分项最多再给 3 分 技能是筛简历的第一道关。看加权比例而不是命中个数，避免「JD 提了 20 项你中了 10 项」被算成高分
职责覆盖度 20 JD 正文切成中文 2-gram，去掉停用字与泛词，看简历覆盖了多少 最容易被忽略的一维：技能全中但做过的事不一样，面试照样挂
经验年限 15 解析 3-5 年 / 3 年以上 / 中文数字，与简历年限比 硬门槛；差一年给大半分，差太多直接扣完
项目相关性 15 取 JD 里权重最高的技术，看它们有没有出现在项目描述里 区分「简历上列了技能」和「真在项目里用过」——后者才是面试能讲的
学历与加分项 10 学历分博士/硕士/本科/大专；JD 的加分项命中再加分 学历是门槛不是竞争力，给太高会让真正的差距被稀释

等级：≥85 高度匹配 / 70-84 匹配度良好 / 55-69 可以投但需补强 / <55 不建议盲投。

关键是校准：分数必须有区分度

第一版跑出来，示例简历 99 分、真实简历 96 分、一份两年经验只会 jQuery 的简历 19 分。看起来「能用」，但 99 和 96 之间没有意义——如果强匹配一律 95+，这个分数就没有信息量了。

调完之后（同一套代码，五组组合）：

JD × 简历 总分 结论
AI 前端 × 示例简历（虚构） 95 高度匹配
AI 前端 × 真实简历（7 年前端） 92 高度匹配
AI 前端 × 弱简历（2 年、大专、jQuery） 19 不建议盲投
后端架构师 × 弱简历 6 不建议盲投
后端架构师 × 真实简历（前端背景） 28 不建议盲投

改了三处才算能用：

1. 覆盖度阈值从 55% 提到 70%。 55% 会让大部分「沾边」的简历都拿满分，这一维等于白算（score = min(20, ratio/0.7*20)）。

2. 项目维度在 JD 没有核心技能时给 8 分，不是白给 10 分。 原来给中性 10 分，结果一份完全不相关的前端简历去投后端岗，光这一项就拿 10 分。

3. 加分项上限从 4 分压到 3 分。 否则「堆加分」可以把硬技能的大缺口盖住。

职责覆盖度：中文 2-gram 的坑

没有分词器，直接用中文 2-gram：把 JD 正文按非汉字切成块，每块取相邻两字成词，去掉停用字（的/了/和/在…）和泛词（负责/熟悉/相关/要求/经验/能力/团队…）之后，看这些特征词有多少出现在简历里。

举一个真实例子：「负责 AI 对话类产品的前端研发」切出来的特征是 对话 / 前端 / 研发 这类词，「负责」「产品」因为太泛被丢掉。这样比对的才是做过什么事，而不是用了什么套话。

这里踩了一个很蠢但很致命的坑：特征词筛选用的是这段正则——

/^\u4e00-\u9fa5\u4e00-\u9fa5/.test(gram)   // 错的，缺字符类方括号

它永远不匹配，特征词数量恒为 0，于是覆盖度永远是 0 分。表现是：总分看着还行，但「职责覆盖」这一栏永远是 0/20，我一开始还以为阈值定太高。改成 /^[\u4e00-\u9fa5]{2}$/ 才对。

技能词表：别名比想象中重要

匹配用「小写化后 includes」，不加词边界——中文里「Vue3 开发」加边界会漏识别。

但别名的坑更多。第一版 Go 的别名只写了 golang，结果 JD 里那句「精通 Go 或 Java」识别不到 Go，一个硬门槛技能被漏掉。后来补成 ["golang", " go ", "go 语言", "go语言"]，并顺手加了微服务、高并发、消息队列、Redis、K8s、分库分表、团队管理几项——不然一份后端 JD 的「缺失技能」会列得莫名其妙。

PDF 解析：两条路，都不出本机

简历来源做了两种：粘贴文本、上传 PDF。PDF 拖进来后在服务端转成文本回填到编辑框，可以先改错字再分析——OCR 和排版提取一定会有串行，直接拿结果去算分数是不负责的。

解析走三段：

  1. Python + PyMuPDF（主路径）：spawn 子进程跑 scripts/pdf-text.py，读回 JSON，超时 10 秒；
  2. 纯 Node 兜底：自己找 stream…endstream，zlib.inflateSync 解 FlateDecode，再抓 (...)Tj 与 [...]TJ 文本指令；
  3. 都失败：返回 422 并提示「请改用粘贴文本」，而不是给一个空结果让人以为分析成功。

临时文件用 mkdtemp 建在系统临时目录，finally 里删干净。整条链路不联网，简历不离开这台机器。

建议：不编造经历

六类建议，按优先级排：缺硬门槛技能（按权重降序）、年限差距、职责覆盖缺口、项目相关性、学历与加分项、优势怎么讲（永远给一条，避免只批评不给出路）。

核心原则写在代码注释里：不编造经历。每条建议都是两条路——

如果确实做过：在相关项目里加一句「[用 XX 做了什么 + 结果是什么（带数字）]」。
如果没做过：花 1-2 天做一个能跑的最小例子，放进个人项目，面试时能讲清原理就够了。

这两句话比「建议补充 Kubernetes 经验」有用得多，因为后者等于没说。

另外给了一块「可直接发送的匹配说明」，把命中的技能、待补项、经验学历、代表作和一句话结论拼成一段，投递时能直接当打招呼消息的第一段。每条建议也能单独复制，方便只取需要的那一句。

怎么跑起来

npm install
npm run build
npm start          # http://localhost:5192

想直接看效果，开 http://localhost:5192/#demo 会自动填入一份虚构的示例 JD 和简历并跑完分析。冒烟测试 npm run smoke 覆盖 36 项：接口、参数校验、超长文本拦截、历史记录增删、PDF 边界（缺数据 / 非 PDF / 损坏文件返回 422）、页面可达。

PDF 想稳定可用，建议装 Python 3 与 PyMuPDF（python -m pip install pymupdf）；没装也能跑，只是复杂排版的提取质量会下降。

已知限制

  • 只有中文：分词是中文 2-gram，纯英文材料效果会打折。
  • 技能是词表匹配，不是语义理解：JD 写「要求熟悉服务端渲染」而词表里只有 SSR 就可能漏。词表在 server/skills.js，加一条是一分钟。
  • 记录存在内存里，最多 20 条，且只留 300 字预览，重启清空——简历不该无声无息地堆在磁盘上。
  • 示例简历里的人物是虚构的，联系方式等字段刻意没写。

一点体会

做完这个项目最深的感受是：打分容易，校准难。任何一套权重都能算出一个 0-100，但只有拿几份明显不同水平的简历去跑，才知道这套权重到底有没有分辨力。95 分和 92 分的差别没有意义，95 分和 19 分的差别才有。

所以我把校准脚本一起留在了仓库里（scripts/_calib.mjs），改权重之后跑一遍、看五组结果有没有被压扁，比凭感觉调参数靠谱。
