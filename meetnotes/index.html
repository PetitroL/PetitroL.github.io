一场会议录音，怎么变成能直接交差的纪要

2026-11-20

「做过会议纪要工具」这句话放在简历上很安全，因为它听起来像是把录音丢给一个大模型就完了。真被追问三句就露馅：说话人是怎么分开的？纪要用的是原文还是模型改写？Word 是拿什么库导的？

所以我把它做成了一个能真跑的完整链路：浏览器现场录音 → 切块转写 → 说话人分离 → 规则生成纪要 → 抽取待办 → 导出 Markdown / HTML / Word。全程在本地跑，不联网、不依赖大模型服务。

源码仓库：PetitroL/meetnotes

真正想解决的问题

开完会最烦的不是开会，是会后的半小时：把录音听完一遍、把谁说了什么记下来、把「下周把接口文档补齐」这种话从一堆闲聊里挑出来、再排成一份能发给领导的文档。

这件事的难点不在「转成文字」，而在把非结构化的口水话变成结构化的交付物。所以我把整个流程拆成了几个彼此独立、每一步都能单独验证的环节，而不是一条黑箱流水线。

三步跑起来

npm install
npm run build
npm start          # http://localhost:5182

进去之后有三种开场：拖音频文件（mp3 / wav / m4a / webm，前端自动转 16k 单声道）、浏览器直接录、或者一键生成一场「产品评审会」的示例会议。第三种是为了让整条链路能被验证——不用去找录音，也能看到逐字稿怎么一段段冒出来、纪要怎么生成。

转写：切块推进 + SSE 逐段显示

音频按 8 秒（3 分钟以内）或 20 秒切块，逐段推进。后端每完成一段就往 SSE 通道推一条 segment，前端边收边渲染，每段都能点回音频的对应位置。

事件设计成 snapshot / status / log / segment / done / failed / updated 七种：snapshot 让刷新页面能接上进度，status 推进度条，segment 增量上屏，updated 表示某段被改过需要同步。这样「边转边看」不是一个假动画，而是真的在接收数据。

说话人：两档可选，默认不装懂

这是我最不想含糊的一块，所以做了两个模式，让用户自己选：

模式 做法 适合
编号模式 按转写稿自带的轮次标 A/B/C，不做声学判断 最稳，会议记录里本来就有轮次
声纹分离 真的从声音里分人：每块估基频，在对数音高轴上聚类 拿到一段没有轮次信息的录音时

声纹分离的实现是这样：对每个音频块做自相关估基频（音高），取 log(pitch) 做一维 k-means，k 不写死，而是 2 到 maxK 逐个试，用轮廓系数挑最好的那个：

const values = voiced.map((c) => Math.log(c.features.pitch));
for (let k = 2; k <= maxK; k += 1) {
  const assign = kmeans1D(values, k);
  const score = silhouette1D(values, assign, k);   // 轮廓系数
  if (score > best.score) best = { k, score, assign };
}
// 分得不够清楚就老老实实按单人处理
if (!best.assign || best.score < 0.15) {
  return { labels: chunks.map(() => "A"), note: `音色差异不够明显…` };
}

为什么只用一维的基频，不做多维特征？ 因为音色差异最直接的体现就是基频，而音量、清浊度这些受麦克风距离和增益影响极大，塞进来反而会把同一个人拆成两簇。维度少，可解释，出错也出得明白。

静音块沿用上一段的标签，最后再做一次平滑去抖——否则一段换气就会被切成两个人。分错了也没关系，界面上能直接给说话人改名（「A → 张工」），改完纪要、待办、导出全部同步。

这条链路里我刻意留了一句提示：音色差异不够明显（轮廓系数 0.32），按单人处理。算不出三声明显的三个人，就承认算不出来，而不是硬分成三个。

纪要：规则生成，所以每句都能回溯原文

不用模型改写，全部按规则挑句，原因很实在：纪要一旦被改写，就没法回溯到「谁在哪一句说的」。而会议纪要里最要命的就是「这话我没说过」。

  • 摘要 3-5 条：按决策词、动作词、数字/时间三类信号给句子打分，挑够分的，按原始顺序排列——不打乱时间线；
  • 议题 2-3 组：用六类主题词表打分归组，同一句话不会被塞进两个议题；
  • 决议 1 条：按决策强度排序取最高分，同分取靠后的那一句——会议尾声才是真正拍板的地方。

每条摘要、每条待办都挂着原句的段落索引，点一下能跳到逐字稿对应位置。我觉得这比「看起来很智能」重要得多。

待办：抽不到就少写，不硬凑

从逐字稿里抽「谁、做什么、什么时候」，靠三样东西：动作词、人称/岗位、截止时间表达。「已经做完了」的句子会被排除掉，避免把已完成的事列成待办。

关键是宁可少写也不瞎补：抽不到时间就只写人和事，抽不到人就只写事，绝不自作主张补一个「本周五」。手改过的待办会被标记，重新计算时不会被冲掉。

Word 导出：零依赖手写 OOXML

这里我没装任何库。因为 .docx 本质就是一个 ZIP，里面装 OOXML——那就自己拼：

// docx = [Content_Types].xml + _rels/.rels + word/document.xml + styles.xml
const files = [
  { name: "[Content_Types].xml", data: Buffer.from(CONTENT_TYPES, "utf8") },
  { name: "_rels/.rels",        data: Buffer.from(ROOT_RELS, "utf8") },
  { name: "word/document.xml", data: Buffer.from(renderDocument(title, blocks), "utf8") },
  { name: "word/styles.xml",   data: Buffer.from(STYLES, "utf8") },
];
return zipStore(files);   // stored（不压缩）方式手写 ZIP，Word 完全认

三种导出各有用途：Markdown 贴进文档 / 飞书，HTML 是单文件自包含的，双击就能看且逐字稿默认折叠，Word 交给要存档的同事。另外还做了一个「复制 Markdown 到剪贴板」，省得为一段文本去下载文件。

怎么证明它真能跑

npm run smoke

这个脚本会自己起服务、建会、跑声纹转写、改名、改段落、待办增删改、再把三种导出逐个校验字节和 MIME，最后删会收尾。当前 42/42 通过。

我现在的习惯是：每个项目都要有一条「一条命令跑完整个链路」的冒烟测试。它不是给别人看的，是给自己改代码时兜底的——尤其是这种多阶段、带异步推送的流程，手动点一遍太容易漏。

已知取舍

  • 会议存在内存里，重启清空（音频文件还在磁盘上）。接数据库是下一步。
  • 逐段之间的延迟是刻意的，为了让「边转边出」这条链路真的成立，不是性能问题。
  • 声纹分离是音色聚类，不是声纹库身份识别。同一人音色变化大时会分错，所以界面允许随时改名。
  • 只做单声道 16k 分析，多声道在前端先降成单声道。
  • 要接真实 ASR，配 ASR_ENDPOINT 与 ASR_API_KEY 即可；没配时走内置演示稿，/api/health 里的 asr 字段会告诉你是哪种来源。

一点体会

这类工具最容易被做成「看起来很智能、实际不敢用」。我的取舍是：每一处判断都留出处，每一处不确定都明说。说话人分不准就提示「按单人处理」，待办抽不到就少写，纪要不用模型改写所以能回溯。把这些说清楚，比做得花哨更能让人敢用。
